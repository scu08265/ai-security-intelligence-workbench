## 一、先把数字说清楚（2026-10-15 当日实测）

| 项 | 读数 | 来源 |
| --- | --- | --- |
| 高优先级队列 | **53** 条（critical 37 + high 16） | `/api/dispositions/metrics` |
| 已复测关闭 | **4** 条 | 同上 |
| 全队列闭环率 | **7.55%** | 同上 |
| 已登记处置 | **6** 条 | 同上 |
| 从未登记处置 | **47** 条 | 同上 |
| 已登记处置内闭环率 | **66.67%** | 同上 |
| 待处置队列构成 | critical 35 + high 12 | `/api/dispositions/pending` |

**两层根源**：

1. **系统里没有任何自动处置流程。** 处置只能人工登记，研判完成后不会自动进入处置流转。
   53 条里 47 条从未被接手，这是比率低的直接原因。
2. **受影响资产是合成资产。** 8 条资产 `is_demo=true`，队列里有 37 条落在
   「演示资产：推理服务 C（合成，配置未知）」。合成资产没有真实补丁动作，
   处置只能"登记"，闭环率天然上不去。

**结论**：7.55% 反映的是**流程覆盖率**，不是处置能力。同样这 6 条登记过的记录里，
4 条已关闭或已接受风险 = 66.67%，那才是处置能力。答辩时两个数要一起讲。

## 四、组员 A（监测、性能与工程化）

### A1（最高优先）用新入口把演示队列真实推进一批，并留下证据

读 `/api/dispositions/pending` 拿到 47 条，逐条判定并分三类：

1. 资产是合成演示资产、动作可判定 → 用批量入口登记 `in_progress` / `fixed`；
2. 资产版本已不在受影响区间 → 单条走 `verified`（触发系统复测，不能批量）；
3. 判定不了或资产本身不真实 → **不登记**，写清原因。

**验收**：登记前后的 `metrics` 读数对照（total / registered / unopened / closure_rate /
registered_closure_rate 五个数）、每条登记的动作与依据（版本变化或工单号）、
以及一份「没登记的是哪些、为什么」的清单。
**不得**把没做的事登记成已闭环。

### A2 把处置流程做成可调度的运行（补上"没有自动处置流程"）

现在处置只能人工登记，没有任何编排。要做的**不是**自动关闭，而是把
「高优先级队列 → 指派 → 复测 → 关闭 / 接受风险」编排成一条可调度的运行记录
（像 `collect` 那样有 run、有状态、有工具调用留痕）：每天对 `open` 队列做一次
到期未处置提醒 + 复测到期扫描，并写进调度器。

**验收**：一条处置类运行的记录 + `scheduler_trace`；`/api/dispositions/pending` 的读数
随运行变化；处置流程每一步都能在运行记录里核查，而不是只存在于脚本里。

### A3 复测闭环的真实性验证（故障注入）

`verified` 关闭依赖 `intelligence.assess_asset` 复测。要用故障注入证明两条边界：
资产仍命中区间时**不能**关闭；资产升级到区间外才关闭。

**验收**：3 条真实复测的 before/after 证据（含
`verification.assessment_status_before/after`）+ 1 条反例（仍命中 → 拒绝关闭）。

### A4 交付收尾

- `reports/ci-validation.json` 仍指向旧 commit，在最新 main 上触发 CI 并写回
  run_id / head_sha / 三个 job 结论。
- 确认连续运行每天都有 `trigger=scheduled` 的记录，给出 `target_met` 回到 `true` 的预计日期。
