# 连续运行重算（2026-10-18）

本文取代 `docs/A_CONTINUOUS_RUN_STATUS_20261015.md` 里对 `target_met` 的估算：
那份是按**旧账本口径**算的，数字不能用。

## 1. 现在的口径

- 只统计 `kind` 属于采集、且 `detail.trigger == "scheduled"` 的运行；
- 窗口是**以今天为终点、往前数 7 个自然日**的滚动窗口，不是"库里一共有多少天"；
- 日界按 UTC 切（北京 08:00 换日）；
- `target_met` 要求窗口内**每个自然日**都有至少一次计划运行。

旧口径的问题：`reliability._date_range()` 会把窗口撑到"首次运行到今天"那么长，
于是 `actual_run_days` / `scheduled_run_days` 实际报的是整个账本（当时 23 天），
看起来"已经连续 7 天"。现在 `competition_scorecard` 把这两个数改成
`scheduled_dates & window_dates`，只数窗口内的天数；连续天数仍然从今天往前数，
两者不再互相冒充。

## 2. 本机账本（成员 A 的机器）

数据取自 `data/intel.sqlite`（sha256 前缀 `a838cc51c4b180fb`），
命令 `tools/check_continuous_run.py --days 7`，产物 `reports/continuous-run-check.json`。

窗口 2026-10-12 → 2026-10-18（UTC），逐日计划运行次数：

2026-10-12 是 0 次；2026-10-13 是 0 次；2026-10-14 是 9 次（1 partial + 8 completed）；
2026-10-15 是 7 次；2026-10-16 是 17 次（含 2 次 partial）；2026-10-17 是 9 次；
2026-10-18 目前 1 次（当天还没过完）。

由此得到四个数：窗口内有计划运行 **5 天**；从今天往前连续 **5 天**；
累计有计划运行 **13 天**；`target_met = false`。

缺口是 **2026-10-12 和 2026-10-13** 两天。这两天是计划任务重挂之前的空档，
不会被回填，也不应该回填。

## 3. `target_met` 什么时候回来

窗口是滚动的：只要最后一个缺口（10-13）还在窗口里，窗口就不完整。

- 以 10-19 结尾的窗口：10-13 → 10-19，仍含 10-13，不成立；
- 以 10-20 结尾的窗口：10-14 → 10-20，缺口全部出窗，**成立**。

所以 **预计 2026-10-20（UTC）回到 `true`**，对应北京时间 2026-10-20 08:00 之后
第一次读到的窗口。前提只有一个：10-14 之后每天至少有一次计划运行。

任何一天整日不开机，ETA 顺延一天——休眠或关机期间计划任务不补触发，
这一点在账本里已经能看到（10-14 只有 9 次、10-15 只有 7 次，都是机器醒着的小时数）。

## 4. 与演示机的差别

任务书里给的读数是"窗口内 6 天、连续 5 天、累计 13 天"，本机是"窗口内 5 天、
连续 5 天、累计 13 天"。差别只在 10-12 或 10-13 里有一天在演示机上有计划运行。
**两种账本的 ETA 都是 2026-10-20**：因为连续天数都是 5，且最后缺口都落在 10-13。

引用时必须带机器限定语；两个环境的逐日账本不要混在同一张表里。
