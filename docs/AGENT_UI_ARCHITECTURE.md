# Codex 式 Agent 工作台：产品架构与交互规范

## 1. 产品定位

本系统是面向 AI 软件供应链安全任务的 Agent 工作台。用户不是在多个报表之间寻找答案，而是用一句任务描述启动一次可观察、可暂停、可复核的工作：系统读取已授权上下文，编排固定工具，形成证据约束下的结论，并把结果沉淀为可视化知识。

产品故事始终围绕赛题主线展开：**发现 AI 软件供应链风险，确认来源证据，关联受管资产，形成处置建议，保留可复核记录**。Codex 式交互是呈现和操作方式，不改变赛题目标，也不把通用聊天能力包装成安全能力。

典型任务可以是：

> 检查最近新增的 AI 组件风险，找出影响我方资产的事件，说明证据缺口，并生成今天的处置清单。

工作台需要让用户同时看懂五件事：当前目标是什么、系统准备怎么做、正在调用什么工具、得到了哪些证据、还需要人决定什么。

## 2. 四层产品模型

四层是同一任务的不同视角，不是四套互相割裂的功能。

| 层级 | 用户看到什么 | 系统职责 | 主要对象 | 边界 |
| --- | --- | --- | --- | --- |
| 输入层 | 任务输入框、上下文附件、范围与约束、建议任务 | 把自然语言任务转换成明确目标和可校验约束 | 任务、资产范围、来源范围、时间窗口、模型开关 | 不接受任意采集 URL；不把模糊要求自动扩大为扫描或攻击动作 |
| 编排层 | 计划、步骤状态、当前执行、暂停点、重试与停止原因 | 按固定流程组织采集、归一、补证、研判和回答 | 任务运行、步骤、角色、预算、状态、耗时 | 角色是同一进程内的职责分工，不宣称多个独立智能体自主协作 |
| 工具层 | 工具调用卡、参数摘要、来源、真实返回、错误、耗时 | 调用后端登记的数据源与本地确定性能力 | 数据源、采集器、检索、富化、研判、评测 | 只调用已登记工具；错误、跳过、部分成功不得被隐藏 |
| 知识层 | 文档库、关系图、证据链、时间线、资产影响矩阵 | 保存、连接并展示事件、证据、资产、结论和文档 | 事件、来源证据、资产、关系、判断、知识文档 | 关系必须有证据 ID；未知显示未知，不由模型补写 |

### 2.1 输入层

输入层是整个界面的主入口，位于任务工作区底部或页面中央的固定输入区。它不是普通聊天框，应包含：

- 主任务：自然语言描述用户希望得到的结果。
- 上下文：已选资产、事件、历史运行或知识文档，可通过引用加入任务。
- 约束：时间窗口、来源范围、是否执行补证、工具调用上限、是否允许模型转述。
- 提交状态：发送、停止当前任务、继续中断任务。

输入框上方可以显示与当前场景相关的建议任务，例如“研判今日新增风险”“解释某事件为何影响该资产”“列出证据缺口”。建议任务只填充输入，不应直接触发写操作。

提交前，界面用一行摘要确认执行范围，例如：

> 将检查最近 24 小时事件；范围为 3 个已授权资产；只使用已登记来源；最多补证 6 条。

若用户没有提供必要条件，系统先展示缺失项并请求补充。资产版本、部署条件或来源证据未知时，不默认推断。

### 2.2 编排层

编排层把一次任务呈现为可审计的运行，而不是只显示一段最终回答。推荐采用纵向步骤流：

1. 理解任务：提取目标、范围和输出形式。
2. 制定计划：列出将执行的步骤、使用的工具类别和停止条件。
3. 获取证据：调用登记来源或读取本地知识。
4. 整理与补证：归一重复事件，保留冲突，检查证据缺口。
5. 关联资产：用组件、版本、暴露面与配置条件进行判断。
6. 形成结果：输出结论、处置动作、引用和局限。
7. 沉淀知识：把运行关联到事件、资产、证据和文档。

每个步骤卡只显示评审需要的信息：状态、责任角色、动作、输入摘要、产出摘要、真实耗时和停止原因。展开后才显示完整工具调用与结构化结果。

状态统一使用：`等待`、`进行中`、`已完成`、`需要确认`、`部分成功`、`失败`、`已停止`。已经结束的步骤不得残留“进行中”。用户停止任务后保留已取得的证据和步骤记录，但未完成部分不能显示为成功。

编排层必须清楚区分：

- **计划**：系统准备执行的动作，可能尚未发生。
- **事实**：工具真实返回或本地数据中已经存在的内容。
- **产出**：归一、研判或回答阶段生成的结构化结果。
- **建议**：基于已有结论给出的下一步动作，仍由人决定是否执行。

### 2.3 工具层

工具层承担“系统如何知道”的解释。每次调用显示为可展开卡片，至少包含：

| 字段 | 展示口径 |
| --- | --- |
| 工具名称 | 用户可理解的动作名称，并保留内部 ID 供审计 |
| 调用原因 | 该调用要补哪项证据或完成哪一步 |
| 输入摘要 | 来源 ID、事件 ID、时间范围等；敏感配置不展示 |
| 状态 | 成功、部分成功、失败、已跳过 |
| 结果摘要 | 抓取、保留、过滤、新增、更新数量或检索命中 |
| 证据产物 | 来源记录、快照哈希、证据 ID、采集时间 |
| 运行信息 | 真实耗时、错误原文、重试次数 |

工具目录按用户目的分组，而不是按代码模块命名：

- 发现工具：从已登记的漏洞、论文、标准与政策来源采集候选内容。
- 查证工具：核对受影响版本、修复版本、严重度、在野利用和官方记录。
- 整理工具：归一、去重、冲突保留、关系抽取和证据完整度检查。
- 研判工具：将事件与已授权资产匹配，生成四档影响结论。
- 检索与回答工具：从本地事件、证据、资产和历史运行中取回信息并组织回答。
- 质量工具：运行本地小样本回归，展示真实执行结果和局限。

来源和工具数量只从运行接口读取，不在产品文案中写死。前端不得提供任意 URL 输入框。调用失败时保留来源、错误和时间，不用空结果冒充成功。

### 2.4 知识层

知识层不是文档列表的别名，而是任务结果的长期可复用结构。一个知识对象应能回到它的来源和生成过程。

核心节点包括：

- 风险事件：CVE、安全公告、论文、标准与政策条目。
- 来源证据：发布者、原文摘录、发布时间、采集时间、快照哈希和可信度。
- 受管资产：组件、版本、暴露面、业务重要性、配置条件和授权状态。
- 判断结论：受影响、不受影响、待确认、不适用，以及理由和证据 ID。
- 处置动作：升级、缓解、补充信息、持续观察等建议及其状态。
- 知识文档：围绕一个主题整理的事件摘要、专题分析、运行报告或处置记录。
- 任务运行：产生或使用这些对象的编排步骤和工具调用记录。

允许展示的关系包括“来源证明事件”“事件影响组件”“资产使用组件”“判断引用证据”“任务生成文档”“文档汇总事件”。任何推断关系都必须显示证据 ID和条件；没有证据的关联只能进入“待确认”，不能画成已确认实线。

## 3. 页面信息架构

主界面采用 Codex 式三栏工作台，并为窄屏提供单栏切换：

| 区域 | 内容 | 目的 |
| --- | --- | --- |
| 左栏：任务与知识导航 | 新建任务、进行中、历史运行、收藏文档、事件与资产入口 | 找到工作上下文 |
| 中栏：任务工作区 | 对话、计划、步骤、工具调用、最终交付、固定输入区 | 完成一次端到端任务 |
| 右栏：上下文与证据 | 当前任务范围、引用、资产、关系摘要、文件/文档预览 | 随时核对依据 |

顶层导航建议保持四个入口：

1. **工作台**：默认入口，创建任务并查看运行全过程。
2. **知识库**：浏览文档、事件、证据和关系图。
3. **资产**：维护受管资产及授权、版本和配置条件。
4. **系统详情**：来源注册、运行健康、AI 参与说明、评测和状态图例。

风险概览与处置清单不必继续作为孤立主导航，它们可以成为工作台的默认任务模板和知识库视图。这样保留现有能力，同时让用户围绕“要完成的任务”行动。

### 3.1 工作台首屏

首屏先回答“现在要做什么”，推荐顺序如下：

1. 任务输入框与三个常用任务模板。
2. 需要立即处理的真实风险、待确认项和失败运行摘要。
3. 最近任务列表，显示状态、范围、结论和更新时间。
4. 选中任务后的编排步骤流。
5. 当前步骤的工具调用和证据产物。
6. 最终交付：结论、资产影响、处置动作、引用和局限。

计数、状态和耗时全部来自接口。没有运行结果时展示空状态和启动建议，不展示演示数字。

### 3.2 知识库页面

知识库提供四种互相联动的视图：

- 文档：按主题、类型、来源、时间和状态筛选，预览引用和关联对象。
- 图谱：展示选中对象的一到两跳关系，默认不铺满全库。
- 时间线：按“发布时间—系统发现—补证—研判—处置”查看过程。
- 矩阵：用事件 × 资产展示影响状态，用筛选控制规模。

从任一视图点选对象，都在右侧打开同一详情抽屉，包含摘要、证据、关系、相关任务和原始来源，避免不同页面给出不同口径。

## 4. 用户任务流

### 4.1 每日风险巡检

1. 用户选择“研判今日新增风险”模板。
2. 输入层带入最近时间窗口和已授权资产范围。
3. 编排层展示计划和来源范围，用户启动任务。
4. 工具层逐项显示采集、整理、补证和研判结果。
5. 知识层更新事件、证据关系和资产影响矩阵。
6. 工作台交付按优先级排列的处置清单，并标出证据缺口和失败来源。
7. 用户打开某结论核验证据，必要时补充资产版本或配置后继续运行。

### 4.2 针对单个事件研判

1. 用户从知识库事件详情点击“发起研判”。
2. 事件和已有证据作为上下文进入输入层。
3. 用户选择资产范围并确认是否补证。
4. 编排层只执行与该事件相关的步骤。
5. 结果用资产影响矩阵展示，并为每个格子提供理由和证据 ID。

### 4.3 证据问答与文档沉淀

1. 用户从事件、资产或知识文档发起问题。
2. 系统先检索本地证据，展示检索范围和命中对象。
3. 回答按结论、依据、局限和下一步组织，每个事实陈述绑定证据。
4. 用户可将本次回答保存为知识文档；文档保留关联任务、引用和生成时间。
5. 若开启模型转述，界面明确标记为“仅改写表达”，该文本不成为新证据。

## 5. AI 的作用与边界

界面应在每次任务中标明哪些内容由规则或工具生成，哪些内容经过模型辅助。

AI 可以：

- 理解用户任务并建议执行计划。
- 在已采集候选中辅助筛选与排序。
- 从本地知识中找到可能相关的事件、资产和历史记录。
- 将已有结构化结论改写为更易读的说明。
- 提醒用户当前信息不足以及可以补充什么。

AI 不可以：

- 凭常识补写版本范围、漏洞利用状态、资产配置或来源事实。
- 把未收录解释为不存在，把未知解释为安全。
- 绕过工具注册表访问任意 URL。
- 自动扩大到未授权资产、主动扫描、漏洞利用或攻击动作。
- 把模型输出当作来源证据，或宣称模型推理已经被验证。
- 在没有真实执行评测时显示分数。

最终结论的可信度来自来源证据、资产事实和可复核规则。模型不可用时，系统仍应完成本地检索、规则研判和证据回答；界面如实显示当前模式。

## 6. 可视化规范

### 6.1 关系图

关系图用于回答“为什么相关”，不用于制造复杂感。默认以用户当前选择的事件、资产或文档为中心，只展示一到两跳关系。

| 元素 | 视觉含义 |
| --- | --- |
| 事件节点 | 风险、论文、标准或政策知识对象 |
| 资产节点 | 已授权或合成演示资产，二者必须有明显标识 |
| 证据节点 | 外部来源记录，可打开原文和快照信息 |
| 文档节点 | 系统整理的主题文档或运行报告 |
| 实线 | 已有证据支持的关系 |
| 虚线 | 待确认关系，必须说明缺失条件 |
| 边标签 | 关系类型，例如“影响”“引用”“使用”“生成” |

图中所有节点都要提供列表等价视图，支持键盘访问。节点数量过多时先聚合，再由用户展开。

### 6.2 证据时间线

时间线至少区分四个时间点：来源发布时间、系统首次发现时间、最近补证时间、最近研判时间。发布时间未知时明确显示未知，不用采集时间代替。

延迟定义为“首次发现时间减来源发布时间”。只有两个时间都存在且可解析时才计算；不得以当前时间或默认值补齐。聚合时同时展示样本数，避免少量事件形成误导。

### 6.3 资产影响矩阵

矩阵行是事件，列是资产，单元格只使用四档状态：受影响、待确认、不受影响、不适用。颜色之外必须有文字或图标标识。点击单元格展示版本比较、条件、判定理由和证据 ID。

矩阵中的空白代表“尚未研判”，不能等同于“不受影响”。默认按处置优先级排序，并允许只看受影响或待确认项。

### 6.4 文档与证据覆盖

文档卡展示文档类型、更新时间、引用数、关联事件数、关联资产数和证据缺口。覆盖率只基于系统定义的证据维度，并展示分子、分母和缺失项；不能把“已登记来源数”当作“已有数据来源数”。

### 6.5 运行与工具轨迹

运行轨迹以纵向步骤为主，工具调用作为步骤内的二级项。一次任务只给一个主进度，避免同时出现多个互相矛盾的进度条。耗时使用后端真实测量值；进行中的任务可以显示已耗时，完成后固定为最终值。

## 7. 数据口径与可信表达

- 事件、资产、来源、运行和评测数量只读取接口返回值。
- “已接入来源”指实际产生有效数据的端点；仅登记但没有数据的来源单独列出。
- 来源失败、限流、缺少 Token、已跳过和部分成功分别展示，不合并为“无新增”。
- 证据引用至少包含来源 ID、发布者、原文或摘录、采集时间；有快照时展示哈希。
- 演示资产必须标记为合成数据，不能与真实受管资产混用。
- 知识文档是对证据的组织，不产生新的事实权威性。
- 任何比例都同时展示统计窗口、分子、分母和未知数量。
- 所有规划中的交互若尚未实现，应在设计稿或文档中标记“规划”，不能写成当前能力。

## 8. 当前能力与演进关系

现有系统已经具备事件、资产、研判、证据问答、来源采集、运行记录、编排信息和知识分类等基础能力。界面演进应优先重组这些能力，而不是重新定义后端事实。

| 当前能力 | Codex 式承载方式 |
| --- | --- |
| 风险总览 | 工作台首页的任务建议与真实状态摘要 |
| 风险处理过程 | 一次任务的编排步骤流 |
| 处置清单 | 任务交付和知识库的资产影响矩阵 |
| 风险与证据 | 知识库事件详情、证据链和关系图 |
| 资产清单 | 独立资产入口及任务上下文选择器 |
| 证据问答 | 工作台输入层与任务对话 |
| AI、工具、来源、质量说明 | 系统详情和每次运行的就地解释 |

第一阶段应先建立统一任务壳、四层清晰标识和知识可视化入口，并复用现有接口。后续若新增持久化任务、可保存文档或关系图接口，应在数据契约落地后再开放对应操作。

## 9. 验收问题

第一次使用系统的人应能在一分钟内回答：

1. 我可以交给这个 Agent 什么安全任务？
2. 当前任务使用了哪些资产、来源和限制？
3. 系统现在执行到哪一步，为什么继续或停止？
4. 哪个工具提供了哪条证据，调用是否成功？
5. 最终结论影响哪些资产，下一步做什么？
6. 一条结论如何回到来源、时间、运行和文档？
7. 哪些内容由 AI 辅助，哪些是确定性工具或规则结果？
8. 哪些信息仍然未知，需要人工补充？
