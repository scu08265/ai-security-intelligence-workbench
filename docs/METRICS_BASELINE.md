# 指标口径基线（交付与答辩唯一基线）

**结论**：本文件确定一件事——凡是写进报告、PPT、答辩口径的数字，基线一律取**队长演示机上的本仓库**
`data/intel.sqlite`，也就是页面 `http://127.0.0.1:8000` 实际读取的那份库。其他机器上的数据库副本
只能作为"各自环境内的过程证据"引用，不再作为对外口径来源。

这样定的原因很直接：评审看到的是页面，页面读的是这份库。口径和展示同源，才不会出现"报告写一个数、
页面显示另一个数"这种自相矛盾。本文件第 2 节由脚本生成，正文任何地方都不要再手写具体比率。

### 3.1 为什么 A 写 0.75、本机不是 0.75

不是算错，是分母不同。A 那份库生成前 `assets = 0`、`assessments = 0`、`assessment_dispositions = 0`，
他是在副本上自行登记处置后才得到 4 条队列，4 条里 3 条关闭，所以是 3/4 = 0.75。
本机这份库的高优先级队列是 53 条（研判总数 192、处置记录 48），已关闭 46 条。
`closure_rate = 已关闭 / 高优先级总数`，两边分子分母都不同，不能互相换算。

**本机这 46 条必须拆开讲**：复测关闭 3 条 + 显式接受风险 43 条。43 条接受风险全部落在
合成演示资产上（无真实补丁可实施），处置记录里逐条写了依据与决策人。
引用时不能说成"修复了 46 条"——页面卡片也是分列的（已复测关闭 / 已关闭合计 / 已接受风险），
报告只能照这个分列写。

## 4. 引用规则

1. 报告与 PPT 的指标表只放第 2 节的数字，并标注快照日期。
2. 任何来自其他机器或数据集的数字，必须紧跟一行限定语说明运行环境；没有限定语的数字不进正文。
3. 口径变了（换机、换库、换语料）先改本文件，再改下游文档。
4. **快照因数据自然增长而过期，不属于第 3 条的"口径变了"**。采集任务每小时写入，所以任何数字
   过一天就会变旧。这种情况直接重跑 `python tools/refresh_metrics_snapshot.py --write`，
   它会同时重写本文件的快照块与 `docs/report/metrics_snapshot.json`，报告读的是同一个文件，
   因此**不需要把报告退回旧值**，也不需要手工核对两处。只有换机、换库、换语料才走第 3 条。
   提交前跑一次刷新，让快照日期等于提交当刻。
