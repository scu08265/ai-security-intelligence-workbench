# 指标口径基线（交付与答辩唯一基线）

**结论**：本文件确定一件事——凡是写进报告、PPT、答辩口径的数字，基线一律取**队长演示机上的本仓库**
`data/intel.sqlite`，也就是页面 `http://127.0.0.1:8000` 实际读取的那份库。其他机器上的数据库副本
只能作为"各自环境内的过程证据"引用，不再作为对外口径来源。

这样定的原因很直接：评审看到的是页面，页面读的是这份库。口径和展示同源，才不会出现"报告写 75%、
页面显示 8.33%"这种自相矛盾。

## 3. 哪些指标能用这条基线，哪些不能

**能（数据就在这份库里）**：采集与定时运行天数、来源健康与成功率、时延分布、语料规模、
处置闭环、告警与调度证据。这些一律以本机读数为准。

**要单独说明来源的**，引用时必须逐条带上"运行环境 + 数据集"限定语，且**不得与上表混排在同一张
指标表里**：

| 内容 | 数据在哪 | 引用时必须怎么写 |
| --- | --- | --- |
| B 的关系抽取 / 问答 / RAG 评测 | 语料已于 2026-10-12 交付到演示机 `D:\ICT\intel-data-b`，按 `MANIFEST.sha256` 核验 47/47 通过 | **可以在演示机上复跑**；引用时注明语料是外部交付、经哈希核验，且语料本身不入库 |
| A 的处置闭环 live 证据（4 条队列 / 3 条关闭 / 0.75） | A 的机器，`D:\新建文件夹\2026-09-26\ba\...\data\intel.sqlite` 的副本，本机不存在 | 注明是 A 机器上的流程落地演示；**交付闭环率写本机口径 48 / 4 / 8.33%** |

2026-10-12 语料到位后，全量测试由 618 passed / 60 skipped 变为 **674 passed / 4 skipped**，
其中包含此前唯一一条已知失败用例（中频词检索）——该缺陷已定位并修复（`9ff7383`），
问题不在词频阈值，而在中文短语的同义词扩展被逐词计分。剩余 4 条跳过依赖两个衍生副本
（`intel-data-b-cvss-20261006`、`intel-data-b-poc-20261002`），这两个副本已于同日随
`B_DERIVATIVE_CORPORA_20261012.zip`（整包 SHA-256 `98bd19c5…961674a`，139 文件）追加交付，
交付机按包内 `MANIFEST.sha256` 核验通过后这 4 条即解除。

两份证据本身都没有造假：它们各自在各自的数据集上成立。问题只在于**不能跨数据集混引**。

### 3.1 为什么 A 写 0.75、本机是 8.33%

不是算错，是分母不同。A 那份库生成前 `assets = 0`、`assessments = 0`、`assessment_dispositions = 0`，
他是在副本上自行登记处置后才得到 4 条队列；本机这份库已有 190 条研判、6 条处置记录，
高优先级 `affected` 条目是 48 条，其中 4 条被复测关闭。`closure_rate = 已关闭 / 高优先级总数`，
分子同量级、分母差一个数量级，结果自然一个是 75%、一个是 8.33%。

## 4. 引用规则

1. 报告与 PPT 的指标表只放第 2 节的数字，并标注快照日期。
2. 任何来自其他机器或数据集的数字，必须紧跟一行限定语说明运行环境；没有限定语的数字不进正文。
3. 口径变了（换机、换库、换语料）先改本文件，再改下游文档。
